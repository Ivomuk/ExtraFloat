Purpose of each diagnostic
max_days_aging_7d
l.max_days_aging_7d
The greatest days_aging reached by the target loan during the seven-day outcome window.

It can be used to:

verify bad_state_1dpd_7d;

inspect the distribution of delinquency severity;

compare alternative thresholds such as >= 1, > 1, or > 3;

identify unexpected values;

distinguish a slight delay from severe delinquency.

Expected consistency check:

bad_state_1dpd_7d = 1
whenever:

max_days_aging_7d >= 1
OR rollover_observed_7d = 1
The source notes define days_aging as time since the 24-hour due point. 

max_days_aging_30d
l.max_days_aging_30d
The highest aging reached by the target loan within 30 days.

It is the primary evidence behind:

bad_state_3dpd_30d
It can be used to:

verify that the > 3 rule was applied correctly;

compare alternative default thresholds;

report delinquency severity;

analyze whether model errors are concentrated around borderline cases;

detect abnormal aging values.

For example, a false positive where max_days_aging_30d = 3 is different from one where it is 0; likewise, a false negative on a loan reaching 30 days overdue is much more serious than one barely crossing the threshold.

rollover_observed_7d
l.rollover_observed_7d
Indicates whether the target loan entered an ANOMALY_OPEN or equivalent anomaly state during its first seven days.

It is useful for:

verifying why a loan was labeled bad even when max_days_aging_7d is null or below 1;

measuring how much of the bad population is caused by rollover rather than conventional aging;

testing whether rollover handling is consistent;

monitoring changes in rollover prevalence over time.

The source exposes both loan_status and is_anomaly_open, so retaining a normalized rollover diagnostic helps reconcile these fields. 

rollover_observed_30d
l.rollover_observed_30d
The same rollover indicator over the 30-day outcome horizon.

It can explain cases such as:

max_days_aging_30d <= 3
bad_state_3dpd_30d = 1
That combination is valid when the loan was labeled bad because it rolled over rather than because it crossed the aging threshold.

It is also useful for decomposing the target:

bad due to aging only
bad due to rollover only
bad due to both aging and rollover
good
For example:

SELECT
    CASE
        WHEN max_days_aging_30d > 3
         AND rollover_observed_30d = 1
        THEN 'aging_and_rollover'

        WHEN max_days_aging_30d > 3
        THEN 'aging_only'

        WHEN rollover_observed_30d = 1
        THEN 'rollover_only'

        ELSE 'good'
    END AS label_reason,
    COUNT(*) AS loans
FROM model_data
GROUP BY 1;
terminal_state_observed_30d
l.terminal_state_observed_30d
Indicates whether a settled, closed, overpaid, or closure state was observed within the outcome horizon.

It helps answer:

Is a good label supported by evidence of repayment, or merely by the absence of an observed bad state?

This is particularly important because:

bad_state = 0
may otherwise mean either:

the loan was genuinely repaid without material delinquency; or

the state history is incomplete and no bad row was captured.

The current repository query explicitly warns that “no overdue or rollover observed” is not automatically equivalent to confirmed repayment unless state coverage is complete. 

You can use this field to categorize good outcomes:

CASE
    WHEN bad_state_3dpd_30d = 0
     AND terminal_state_observed_30d = 1
    THEN 'confirmed_good'

    WHEN bad_state_3dpd_30d = 0
     AND terminal_state_observed_30d = 0
    THEN 'unconfirmed_good'

    ELSE 'bad'
END
Depending on warehouse semantics, you might eventually require a terminal state for a confirmed good label—or retain unconfirmed outcomes with a separate confidence flag.

outcome_state_row_count_30d
l.outcome_state_row_count_30d
The number of physical target-loan state rows matched during the outcome interval.

It helps detect:

duplicate daily state records;

loan-matching errors;

unexpectedly sparse histories;

unexpectedly high row counts;

source-ingestion changes.

This is a row-count diagnostic, not proof of 30 complete days. Multiple rows can exist on one date, which is why the distinct-date count is also retained.

outcome_observed_date_count_30d
l.outcome_observed_date_count_30d
The number of distinct calendar dates on which the target loan was observed during the outcome window.

It helps:

measure state-history coverage;

detect incomplete extraction;

compare coverage between train and validation periods;

investigate whether label rate varies with the amount of observed history;

determine whether good labels are disproportionately based on sparse evidence.

However, fewer than 30 observed dates does not necessarily mean incomplete data. A loan settled on day 1 may legitimately stop appearing. This diagnostic must therefore be interpreted with terminal-state information.

A useful audit is:

SELECT
    terminal_state_observed_30d,
    outcome_observed_date_count_30d,
    COUNT(*) AS loans,
    AVG(CAST(bad_state_3dpd_30d AS DOUBLE)) AS bad_rate
FROM model_data
GROUP BY 1, 2
ORDER BY 1, 2;
The current repository query uses distinct observed dates as an eligibility proxy, requiring at least five of seven dates.  Retaining the diagnostic lets you assess whether such a rule is justified instead of silently imposing it.

first_outcome_state_date
l.first_outcome_state_date
The earliest matched state date for the target loan.

It helps identify:

delayed first observations;

a failure to match the disbursement-day record;

incorrect loan-start dates;

source ingestion gaps;

matching problems around month boundaries.

For example:

DATE_DIFF(
    'day',
    loan_date,
    first_outcome_state_date
)
should usually be small. A large delay deserves investigation.

last_outcome_state_date
l.last_outcome_state_date
The latest state date observed for the target loan within the label horizon.

It helps determine whether:

the loan remained open throughout the horizon;

the loan disappeared from state data early;

the disappearance coincides with a terminal state;

the observation window was truncated;

matching stopped unexpectedly.

For a settled loan, an early last date can be perfectly valid. For a non-terminal loan, an early last date might indicate missing data.

post_disbursement_observed_date_count_7d
l.post_disbursement_observed_date_count_7d
The number of distinct calendar dates observed strictly after the loan date, within the 7-day outcome window (day 0 excluded). The 30-day sibling of this column, post_disbursement_observed_date_count_30d, already existed; this is its 7-day counterpart, added so the same observability check can be run at either horizon.

Label-eligibility columns (bounded coverage ratio + near-horizon gate)

The columns below implement the asymmetric censoring policy used to derive label_eligible_30d: a known bad is trusted regardless of follow-up completeness, but a "good" label requires bounded, near-horizon observation evidence before it is trusted. See data/loan_state_query_updated_materialized.txt's statement-4 header comment for the full policy write-up.

observed_closure_date_30d
l.observed_closure_date_30d
The earliest closure_date genuinely observed (state_date >= closure_date, ruling out a backfilled/provisional value) within the 30-day horizon. NULL if no closure was observed in-window.

closure_observation_state_date_30d
l.closure_observation_state_date_30d
The state_date on which observed_closure_date_30d was first recorded. Useful for spotting ingestion latency between when a loan actually closed and when that closure became visible in the state feed.

required_observation_end_date_30d
l.required_observation_end_date_30d
The date through which follow-up is required for this loan: the observed closure date if one occurred in-window, otherwise the full label_horizon_30d_end. A loan that closes early gets a correspondingly shorter, achievable observation requirement instead of always being held to the full 30 days.

expected_observed_date_count_30d
l.expected_observed_date_count_30d
DATE_DIFF('day', loan_date, required_observation_end_date_30d) -- the denominator of follow_up_coverage_ratio_30d.

observed_date_count_to_required_end_30d
l.observed_date_count_to_required_end_30d
The number of distinct calendar dates actually observed, strictly after loan_date, up through required_observation_end_date_30d. The numerator of follow_up_coverage_ratio_30d.

last_state_date_to_required_end_30d
l.last_state_date_to_required_end_30d
The latest state_date observed, strictly after loan_date, up through required_observation_end_date_30d. Feeds near_horizon_observation_30d.

follow_up_coverage_ratio_30d
l.follow_up_coverage_ratio_30d
observed_date_count_to_required_end_30d / expected_observed_date_count_30d. NULL only when expected_observed_date_count_30d is 0, which should never happen for a valid observation window (required_observation_end_date_30d is constructed to always be strictly after loan_date) -- a NULL here is a data-integrity signal (label_eligibility_reason_30d = 'CENSORED_INVALID_OBSERVATION_WINDOW'), not ordinary censoring.

meets_coverage_ratio_30d
l.meets_coverage_ratio_30d
1 iff follow_up_coverage_ratio_30d >= 0.8. This is the single place the 0.8 threshold is evaluated; every other coverage-related column (fails_coverage_ratio_30d, confirmed_good_30d, label_eligibility_reason_30d) derives from this boolean rather than re-checking the literal.

near_horizon_observation_30d
l.near_horizon_observation_30d
1 iff at least one post-disbursement date was observed and the last such date falls within 5 days of required_observation_end_date_30d. Distinguishes "confirmed good" from "we simply stopped observing this loan".

same_day_settlement_observed_30d
l.same_day_settlement_observed_30d
1 iff a terminal status (SETTLED/CLOSED/OVERPAID) was observed with a known, near-zero balance (outstanding_ugx IS NOT NULL AND outstanding_ugx <= 0.01) on state_date = loan_date itself (day 0) -- the one date every other post-disbursement column above deliberately excludes. This is a 24-hour agent-float product, so same-day settlement is the expected best outcome, not sparse follow-up: the source table stops emitting rows for a loan_uid the day after it closes, so observed_date_count_to_required_end_30d (gated to state_date > loan_date) is structurally always 0 for such a loan, and it could never reach confirmed_good_30d = 1 via the normal coverage-ratio path without this independent signal. The NULL-balance check fails closed (an unknown balance is never treated as zero).

confirmed_good_30d
l.confirmed_good_30d
1 iff bad_state_3dpd_30d = 0 AND (
  (observed_date_count_to_required_end_30d > 0 AND meets_coverage_ratio_30d = 1 AND near_horizon_observation_30d = 1)
  OR same_day_settlement_observed_30d = 1
). The "good" half of the asymmetric censoring rule -- deliberately stricter than merely "not observed bad" -- with same-day settlement OR'd in as an independent alternative path alongside the normal bounded-coverage-ratio path.

has_post_disbursement_state_30d
l.has_post_disbursement_state_30d
1 iff observed_date_count_to_required_end_30d > 0 -- whether any post-disbursement state was observed at all, independent of coverage ratio.

fails_coverage_ratio_30d
l.fails_coverage_ratio_30d
The complement of meets_coverage_ratio_30d (1 iff meets_coverage_ratio_30d = 0). Provided as an explicit failure flag alongside label_eligibility_reason_30d, since the prioritized reason code can't simultaneously express every independent failure condition for a row.

fails_near_horizon_30d
l.fails_near_horizon_30d
The complement of near_horizon_observation_30d. Same rationale as fails_coverage_ratio_30d.

label_eligible_30d
l.label_eligible_30d
1 iff bad_state_3dpd_30d = 1 OR confirmed_good_30d = 1. This is the column pd_model/preprocessing/loan_history_features.py filters on to build the modelling population -- every CENSORED_* row (label_eligible_30d = 0) is dropped before bad_state is derived, but is retained in the full audit export (df_diagnostics) for review.

label_eligibility_reason_30d
l.label_eligibility_reason_30d
One of: KNOWN_BAD, CONFIRMED_GOOD_SAME_DAY, CONFIRMED_GOOD_TERMINAL, CONFIRMED_GOOD_HORIZON, CENSORED_NO_POST_DISBURSEMENT_STATE, CENSORED_INVALID_OBSERVATION_WINDOW, CENSORED_SPARSE_FOLLOW_UP, CENSORED_EARLY_LAST_OBSERVATION, CENSORED_OTHER. A prioritized, human-readable explanation of why label_eligible_30d has the value it does -- useful for auditing the censored population's composition (e.g. is exclusion dominated by sparse follow-up or by early-observation cutoff?). CENSORED_INVALID_OBSERVATION_WINDOW should never appear in a healthy build; a nonzero count is a build-blocking data-integrity failure, not routine censoring.

Primary target
bad_state_3dpd_30d = 1
if the target loan ever has:

days_aging > 3
OR ANOMALY_OPEN
during the 30 days after disbursement.

It means:

The target loan became more than three days overdue or entered rollover/anomaly status at any point in the 30 days following disbursement.
It marks the target loan bad if it becomes more than three days overdue or enters rollover state within 30 days.

Secondary target
Also retain:

bad_state_1dpd_7d
to measure any breach of the product’s 24-hour obligation.

It means:

The target loan breached its 24-hour obligation by at least one aging day or entered rollover status within seven days.
It identifies any breach of the 24-hour obligation during the following seven days. The source description says days_aging measures time since the 24-hour due point.
